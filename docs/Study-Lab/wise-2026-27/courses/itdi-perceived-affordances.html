Actual and perceived affordances

Explain the mechanism

An affordance concerns a possibility for action in a relation between an actor and an environment or artifact. It is not simply a benefit or a button. A chair may support sitting for one actor but not another; perception is a further question. Gibson’s ecological perspective emphasizes that an action possibility need not be noticed or exercised to exist. Norman shifts attention toward what users believe an interface lets them do.

This distinction matters because successful interaction needs more than technical availability. A user can fail to discover an available action, or expect an action that the system does not support. A visible button is a cue; the goal-oriented action it suggests and the actual system behaviour must still be examined. An attractive label does not establish that the corresponding action is available.

The lecture retains a debate between dispositional and relational accounts. Its later course definition stresses relations, sociotechnical context and possibilities for action. Do not silently turn the early emphasis on objective existence into the claim that every actor has identical possibilities. Also distinguish possible, perceived and actually performed: none entails the next automatically.

Worked example

Consider an own hypothetical document app. An editor can restore a previous version through an unlabelled history icon. A novice does not recognize it. Restoration is available for that editor, but not perceived. Adding “Version history — restore” can improve discovery without adding restoration functionality.

Now a read-only guest sees the same icon but cannot restore anything. Better wording alone cannot grant permission. A label promising restoration would instead create a mismatch for the guest. A suitable design could show “View history” and explain why restoration requires an editor role. Check the action with each role, then ask users what they expect before they click. Successful discovery is evidence about perception; successful restoration is evidence about the tested action, not about every user or context.

Understanding pathway

Own exercises, not official assignment tasks. Write your attempt before revealing help. Assess reasoning with the criteria, not keyword matching. These tasks emphasize conceptual application; inventing numerical precision would not establish understanding.

1. Reconstruct three distinctions

Your attempt: Without looking back, distinguish an available action, a perceived action and an enacted action using restoration. Explain why an unused function can still matter.

Optional hint

Think about the editor before and after noticing the icon.

Complete worked answer and criteria

Restoration can be available to the editor before it is noticed. Perception is the belief that restoration can be done. Enactment is actually restoring a version. Non-use alone therefore does not show absence: the editor might not discover the option or might not need it.

Assessment: Three distinctions and explanation of non-use: 1 point each (4).

2. Design a diagnostic test

Your attempt: An editor fails to restore a file. Construct a test that separates a discovery problem from a permission or functionality problem. State what observations would support each diagnosis.

Optional hint

Test a specific actor and file, not an abstract user.

Complete worked answer and criteria

First verify the editor role and test restoration on a controlled file with the same account. Then ask the participant to explain the icon and attempt restoration without guidance. If controlled restoration works but the participant cannot locate it, discovery is a plausible problem. If the participant predicts restoration but receives a permission failure, expectations and available action diverge. If the role is valid but restoration fails for the tester too, investigate the implementation. Record conditions and avoid concluding from one test that all users are identical.

Assessment: Controlled action, unguided expectation test, discovery observation, technical/permission observation, scope boundary: 1 point each (5).

3. Diagnose a misleading conclusion

Your attempt: “Nobody clicked the history icon, so restoration is not an affordance. We should add a brighter icon and promise recovery to all accounts.” Identify two errors and repair the recommendation.

Optional hint

Separate evidence of use from evidence of possibility.

Complete worked answer and criteria

No clicks do not establish no possibility: users may not notice it or need it. A brighter icon changes signalling, not permissions; promising recovery to guests is unsupported. Test relevant tasks and roles, make the editor action discoverable and describe the guest limitation accurately.

Assessment: Non-use error, cue/permission distinction, role-sensitive repair, testable evidence: 1 point each (4).

4. Transfer to an irreversible action

Your attempt: Replace restoration with permanent deletion. Editors may delete, guests may not. Explain why maximizing clicks is the wrong objective and propose a role-sensitive assessment.

Optional hint

Discoverability is not the same as encouraging every possible action.

Complete worked answer and criteria

Editors should understand the deletion option and its irreversibility before acting, not be nudged into accidental deletion. Guests should not receive a false promise of deletion authority. Test whether each role predicts the result correctly, whether confirmation explains the consequence, and whether unintended deletion is avoided. A confirmation is a design proposal, not a guarantee of safety; test comprehension and actual behaviour. The technical permission model remains separate from the cue.

Assessment: Irreversibility, editor understanding, guest boundary, suitable observation, no guaranteed outcome: 1 point each (5).

Error reflection and delayed retrieval

Maximum 18 self-assessed points (4 + 5 + 4 + 5). Record one conflation in your first attempt: which actor, condition or causal step did you omit? Rewrite it as a conditional explanation. Correct labels without the requested reasoning do not earn reasoning points. Tomorrow: reconstruct the mechanism and solve task 2 unaided. In one week: repeat task 4 with the permission, audience or review rule reversed; explain which parts of your answer no longer hold.
